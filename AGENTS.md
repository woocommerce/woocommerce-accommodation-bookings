# WooCommerce Accommodation Bookings Agent Guide

This file is the primary instruction source for coding agents in this repository.

## Backward Compatibility

Any change to a **public or externally exposed** class, function, or method signature is **high-risk** and **must state its backward-compatibility impact in the PR description**. This plugin gives you no privacy boundary to hide behind: there are no namespaces anywhere in `includes/`, so every class lives in the global namespace under the `WC_Accommodation_*` and `WC_Product_Accommodation_Booking*` prefixes. A `private` member is internal; a `public` or `protected` method on a loaded class is reachable by anything else on the site.

Treat a symbol as **externally exposed** when it is implemented or consumed outside this repository - by other plugins, themes, or site snippets - even if it looks internal. When in doubt, assume it is exposed and state the BC impact.

**The plugin publishes no interfaces today.** If you add one, adding a method to it later is backward-incompatible: existing implementers fatal on load because they no longer satisfy the contract. Removing a required method is breaking too - implementers carry a now-dead method, which static analysis such as PHPStan will flag. Prefer a non-breaking alternative: add the method to the concrete class rather than the interface, introduce a separate new interface, or supply a default implementation via an abstract base class.

**Inheritance is the live version of that risk here.** `WC_Product_Accommodation_Booking extends WC_Product_Booking` and `WC_Product_Accommodation_Booking_Resource extends WC_Product_Booking_Resource`, and both exist to override parent methods: `get_type()`, `get_resources()`, `get_price_html()`, `get_time_slots()`, `get_blocks_in_range()`, `get_duration()`, `get_base_cost()`, `get_block_cost()`. Third-party code subclasses these in turn. The same applies to *which* methods get called: adding a fast path that skips an overridable method silently disables a subclass's override even though no signature changed.

**Deprecate, don't rename.** For existing public symbols (classes, methods, constants, hooks, the product type slug), never rename or remove them in place. Mark the old symbol `@deprecated`, introduce the replacement alongside it, and keep both working through a deprecation window so external consumers have time to migrate.

> This rule exists because WooCommerce 10.9.0 was reverted on WP Cloud: a required method added to a published contract fataled every older extension that implemented it. The same failure mode applies to any contract this plugin publishes.

### The compatibility surface is wider than PHP signatures

WordPress exposes more contracts than class and function signatures. The following are equally binding: a change to any of them is **high-risk** and requires the same backward-compatibility impact statement in the PR description.

**The `accommodation-booking` product type slug is this plugin's largest contract.** It is persisted on every accommodation product as its `product_type` term, and it is not merely a string in the code: it derives the data store key `product-accommodation-booking` registered through `woocommerce_data_stores`, the dynamic template hook `woocommerce_accommodation-booking_add_to_cart`, and the type checks that gate nearly every filter callback in `includes/class-wc-accommodation-booking.php`. Renaming it orphans every existing accommodation product on every installed site - those products stop resolving to `WC_Product_Accommodation_Booking` and fall back to a plain product. It is not renameable without a data migration. Treat the `_wc_accommodation_booking_*` post meta keys the same way: they are stored on live products and read by anything querying them from outside.

**Hooks and filters are public contracts.** Every `do_action` and `apply_filters` call is an interface that third-party callbacks depend on, including this plugin's own hooks. The admin rate views fire `woocommerce_accommodation_bookings_after_display_cost`, `woocommerce_accommodation_bookings_after_booking_base_cost`, `woocommerce_accommodation_bookings_after_bookings_pricing`, and `woocommerce_accommodation_bookings_after_booking_pricing_override_block_cost`; the filters are `woocommerce_accommodation_booking_get_check_times`, `woocommerce_accommodation_booking_time_tab_title`, `woocommerce_accommodation_booking_time_tab_heading`, `woocommerce_accommodation_bookings_range_picker_enabled`, `woocommerce_accommodation_bookings_docs_url`, and `woocommerce_accommodation_bookings_support_url`. Removing a hook, renaming it, or removing/reordering its arguments breaks every attached callback. Changing *when* or *whether* a hook fires can break consumers that depend on its timing. Additive is the safe path: append new arguments at the end, never remove or reorder existing ones. To retire a hook, fire it through `do_action_deprecated()` / `apply_filters_deprecated()` for a deprecation window instead of deleting it.

**Never trust data that flows through hooks.** Keep hook callback parameters untyped and validate or coerce the value before passing it to strictly typed code, since any callback can receive a value another one produced. And when firing a filter, validate the final return value before using it, since any callback in the chain can return the wrong thing.

**Registered script and style handles are public contracts.** Third-party code enqueues plugin handles and lists them as dependencies, including handles that were only ever registered incidentally. `wc_accommodation_bookings_writepanel_js` is the handle this plugin registers, on the product admin screens where extensions are most likely to attach. To rename with a compatibility window, register the legacy handle as an alias that depends on the new handle; do not register the same file under both handles, or pages with mixed consumers will load it twice.

**This plugin is a guest inside WooCommerce Bookings, and that cuts both ways.** It owns almost no booking behaviour of its own: it hooks roughly twenty Bookings filters (`woocommerce_bookings_product_types`, `get_booking_products_args`, `get_booking_products_terms`, `woocommerce_bookings_get_start_date_with_time`, `woocommerce_bookings_find_booked_day_blocks`, `wc_bookings_product_duration_fallback`, and the rest), subclasses two Bookings product classes, and writes directly to Bookings' `{$wpdb->prefix}wc_booking_relationships` table and Core's `{$wpdb->prefix}wc_product_meta_lookup`. Those are someone else's contracts, with two consequences:

- Do not assume a Bookings hook or method still behaves as it did. Verify against the installed Bookings version rather than against what an override implies, and prefer widening a type check over narrowing one.
- `WC_Accommodation_Dependencies::check_dependencies()` sets the supported floor - currently Bookings `1.9.0`, read from the `wc_bookings_version` option, alongside an active-plugin check that still tolerates the misspelled `woocommmerce-bookings.php` filename shipped by Bookings 1.9.10 and earlier. Raising that floor deactivates the plugin for merchants below it. That is a breaking change for them, not a cleanup: state it in the PR and say why the floor has to move.

**Version-keyed data updates are one-shot.** `WC_Accommodation_Bookings_Plugin::install()` runs on `shutdown` and gates its data updates on a `version_compare()` against the `wc_accommodation_bookings_version` option - see the existing `1.1.3` pricing conversion. A site that already stored a version past your gate will never run your update. A migration added after that version has shipped needs a new gate, and a gate must never be ahead of the version it ships in.

**Do not assume global state.** `install()` runs on `shutdown`, which fires in every context - front end, admin, REST, cron, and WP-CLI - and product code is reached from all of them plus the cart and checkout. Those contexts do not all set the globals a front-end request does (`$post`, `$wp_query`, an initialised session or cart). Note also that `_register_hooks()` loads the admin and REST includes behind `is_admin()` plus a raw `wp-json/wc-bookings` substring check on `REQUEST_URI`, so anything placed in those files is simply absent on other REST routes, on cron, and under WP-CLI. A newly introduced read of a global, or of `WC()->…` state, in a path reachable outside a standard request is a fatal or a silent misbehaviour in the contexts that do not set it. Guard the exact dependency explicitly: `function_exists`/`class_exists` for symbols, `isset` for variables, `did_action` for lifecycle state, and verify that `WC()` and the required component are initialised before dereferencing `WC()->…`.

**Do not assume single-site.** Multisite changes where data lives: site-scoped vs network-scoped options (`get_option` vs `get_site_option`), per-site tables, user roles and capabilities, and upload paths all differ. This plugin stores `wc_accommodation_bookings_version` and reads `wc_bookings_version` with `get_option`, so both are site-scoped and every data update runs once per site - a network-activated install upgrades sites independently, and a site created later starts from an unset version. `WC_Accommodation_Dependencies::init()` already accounts for this by merging `active_sitewide_plugins` into its plugin list; keep new dependency checks doing the same. A change that reads or writes site state must state in its PR whether it behaves correctly under multisite - and if it was not tested there, say so explicitly.

**Do not assume install layout.** WordPress could be configured to run in a subdirectory, with relocated `wp-content`, and behind reverse proxies. Never build paths or URLs by concatenation from the domain root; derive them (`plugins_url()`, `plugin_dir_path()`, `wp_upload_dir()`, and mind the `home_url()` vs `site_url()` distinction). `WC_ACCOMMODATION_BOOKINGS_INCLUDES_PATH`, `WC_ACCOMMODATION_BOOKINGS_TEMPLATE_PATH`, and `WC_ACCOMMODATION_BOOKINGS_PLUGIN_URL` are already derived this way - use them instead of rebuilding a path, and keep them derived. A path that works on a root install and breaks elsewhere is a compatibility bug, not an edge case.

### Before changing any public or externally exposed surface (agent checklist)

1. Identify the contract you are touching: signature, override, hook, script handle, the product type slug or a meta key, a Bookings contract you consume, a version gate, global/scope expectation, site topology, or install layout.
2. Assume unseen consumers. You cannot enumerate third-party code; if the surface is reachable from outside this plugin, someone consumes it.
3. Prefer the additive path (new optional method, appended hook argument, new symbol + deprecation) over changing what exists.
4. State the impact in the PR description: what changed, who could consume it, and why it is safe or what the deprecation path is.
5. If you cannot establish the impact, stop and flag it to the user as needing review.
